# 超越极限 · 战斗引擎开发复盘

## 项目概述

"超越极限"是一款六边形网格同步回合制 Roguelike 对战游戏的战斗引擎 demo。采用纯 ES 模块架构，WebRTC DataChannel P2P 联机，确定性锁步协议。三名职业（法师/战士/射手），46 项技能，139 项自动化测试。

开发周期中，AI 端承担了全部代码编写、架构设计、测试维护、UI 渲染和网络协议实现。本文档从人机协作的视角复盘开发过程中的得失与经验。

---

## 一、做得好的地方

### 1. 声明式技能数据 + 机械翻译器

这是整个项目最成功的架构决策。

**设计**：`SkillData.js` 中所有技能以纯 JSON 风格数据对象定义，`SkillResolver.js` 机械地遍历 effects 数组产出 CommandSequence，`TurnManager.js` 按 cmd type 分发执行。三层完全解耦。

**收益**：新增一个技能只需要写约 15 行声明式数据，不用碰任何逻辑代码。从"美式居合"到"枪舞全屏四联射"，每次改动都在 2 分钟内完成，139 项测试自动验证没有回归。如果每个技能是手写 if/else 分支，这个迭代速度不可能做到。

**可复用的经验**：

> 内容驱动型游戏（技能、道具、状态效果）应该优先建立 **data → interpreter → executor** 的三层分离架构。宁可前期多花时间设计 effect schema，也不要边加技能边写特判。好的 schema 让后续内容创作变成填表工作。

---

### 2. 确定性锁步从一开始就设计进去

**设计**：Speed tier 分组 + 同 tier 内按 `actorId` 字母序排序 + `seededRandom` LCG 驱动所有随机元素。

**收益**：P2P 双方只要输入相同就输出相同。整个开发过程中没有出现"为什么两边结果不同"的联机同步 bug。

**可复用的经验**：

> 联机游戏的确定性边界要在架构阶段划定。随机数、排序、浮点精度——这是锁步 bug 的三大来源，越早处理成本越低。不要在后期修补确定性。

---

### 3. 统一伤害载体 pipeline

**设计**：用投射物（Projectile）作为所有伤害的载体。全屏 AOE 通过 `SPAWN_STATIONARY_AOE` 在每格生成静止投射物，线性攻击通过 `ATTACK_LINE` 展开为多个独立投射物。摒弃了直接扣血的 `ATTACK_GLOBAL`。

**收益**：弹壳掉落、纳刀拦截、路径拾取、维度穿越——所有这些子系统对全屏技能和单体技能一视同仁。没有特殊通道，就没有特殊 bug。

**可复用的经验**：

> 当发现一个功能绕过了现有的 pipeline（如 ATTACK_GLOBAL 直接扣血绕过了投射物拦截），说明 pipeline 抽象本身是对的，应该让新功能走 pipeline 而不是另开一条路。统一的计算载体是游戏引擎可扩展性的基础。

---

### 4. Hook 驱动的 Buff 系统

**设计**：`BuffManager` 不靠每回合遍历所有 Buff 来判断触发时机，而是在 `apply` 时根据 statusType 注册对应的 HookName 处理器。`LOCKED` 注册 `ON_BEFORE_MOVE` 返回 false，`COVERING_FIRE` 注册 `ON_ALLY_ATTACKED` 插入反击。TurnManager 不需要知道任何具体 Buff 的存在。

**收益**：新增状态效果只需在 `StatusEffectDefs.js` 添加定义 + 在 `BuffManager._registerHooks` 添加一个 case。管线代码零侵入。

**可复用的经验**：

> 状态效果应该用"订阅系统事件 + 修改上下文"的模式实现，而不是在管线代码里写 `if (hasBuff(LOCKED)) return`。前者让新 Buff 可以零侵入添加，后者会让管线代码最终变成不可维护的意大利面条。钩子返回值语义（false=阻止，undefined=透传，对象=修改上下文）要在一开始就定义清楚。

---

### 5. 测试即契约

**设计**：139 项测试覆盖全部 46 个技能的基本行为 + 10 个重赛状态机场景。每次改动后跑一次 `node tests/skill_test.js`。

**收益**：在快节奏迭代中充当安全网。所有 def/gun_dance/grapnel 的重构都在测试保护下完成，零回归。

**可复用的经验**：

> 即使只是 demo 项目，也应该在技能数量超过 10 个时就建立自动化测试框架。边际成本递减——前 5 个测试需要搭框架，之后每加一个技能多 5 行测试代码，但每次改动能防止 5 个回归 bug。测试即文档：重赛状态机的 10 个测试场景比任何文字描述都更精确地表达了预期行为。

## 二、需要改进的地方

### 1. 技能语义澄清不够及时

**问题**：次元斩和枪舞都经历了多轮修正——
- 次元斩：AI 端先解释为全屏攻击，用户纠正为"正向连线 + 反向射线"
- 枪舞：先做成 HEX 四连射，用户纠正为全屏 AOE，再纠正为 4 弹壳而非 1 弹壳

每次都是用户看到实现后再纠正，说明 AI 在动手前没有向用户确认理解是否正确。

**改进方向**：

> 对于名字或描述含糊的技能，AI 端应该**先用一行中文描述打算怎么实现**，让用户确认，再写代码。一行中文描述比 50 行代码更值得先发出来。"假设确认"步骤不能省。

---

### 2. 单一文件膨胀过快

**问题**：`index.html` 达到 1992 行，混合了 CSS、HTML 骨架、渲染逻辑、网络代码、输入处理。到开发后期，查找和修改一个特定功能需要在文件中大量上下翻屏。

**改进方向**：

> 即使是 demo 项目，也应该在单文件超过 500 行时就拆分为独立模块（如 `renderer.js` / `panels.js` / `input.js` / `network-ui.js`）。拆分成本随时间线性增长，但推迟拆分的导航成本指数增长。

---

### 3. Plan 文件跨 session 残留

**问题**：Plan mode 结束后，旧计划文件仍然出现在新 session 的系统提示中。AI 端误以为要继续执行旧计划（UI 配色/翻页调整），用户立刻叫停。

**改进方向**：

> 跨 session 恢复时，AI 端应主动确认旧计划是否仍需执行。计划完成后应有明确的"已关闭"标记，避免残留在上下文中误导后续 session。这是工具链层面的改进空间，也是 AI 行为层面的注意事项。

---

### 4. 缺少可视化调试手段

**问题**：整个开发过程中，调试完全依赖测试断言和日志字符串。投射物路径是否正确、弹壳是否落到了正确位置、AOE 范围是否覆盖了预期格子——这些只能通过阅读代码逻辑和数字推断。当"全屏AOE从(0,-2)出发半径6是否覆盖所有棋格"这种问题出现时，纯靠手动计算 hexDistance 来验证。

**改进方向**：

> 做格子/战棋类游戏时，花半天做一个 debug 渲染层（不同颜色画碰撞检测范围、弹壳分布热力图、投射物路径线）会在后续数周的开发中持续回本。可视化调试不是 nice-to-have，而是网格游戏的开发效率杠杆。

## 三、可复用的开发原则

| 优先级 | 原则 | 说明 |
|--------|------|------|
| **P0** | 先建 data schema，再写内容 | SkillData 的 effects 结构是项目骨架。骨架对了，加内容像填表 |
| **P0** | 确定性边界早定 | 不要等联机 bug 出现才加 seeded random 和确定性排序 |
| **P0** | 测试即安全网 | 技能数超过 10 就建立测试框架，每次改动后必跑全量测试 |
| **P1** | AI 端实施"假设确认" | 对含糊需求先描述计划再写代码。一行中文胜过百行代码 |
| **P1** | 单文件超 500 行就拆 | 宁可多几个小文件，不要让单体文件成为导航负担 |
| **P1** | 统一计算载体 | 所有伤害走同一个 pipeline，不为"特殊效果"开例外 |
| **P2** | Plan mode 结束后标记关闭 | 避免跨 session 残留误导 |
| **P2** | 格子游戏做 debug 渲染层 | 半天投入，数周回报 |
| **P3** | Hook 优于硬编码分支 | 状态效果用事件订阅模式，管线代码零侵入 |

## 四、关键决策回顾

| 决策 | 当时的选项 | 选择 | 后果评估 |
|------|-----------|------|----------|
| 全屏AOE实现方式 | ATTACK_GLOBAL（直接扣血）vs SPAWN_STATIONARY_AOE（每格投射物） | SPAWN_STATIONARY_AOE | 正确。统一了弹壳、拦截、拾取 pipeline |
| 次元斩实现 | 独立 ATTACK_GLOBAL vs 展开为多投射物 | ATTACK_LINE 展开 | 正确。每格独立投射物可被纳刀逐个拦截 |
| 悬剑落剑时机 | 回合开始 vs speed-2 阶段 | speed-2 | 正确。速2落剑与速1技能有合理的先后关系 |
| 弹壳拾取范围 | 仅落脚点 vs 路径每格半径1 | 半径1 沿线拾取 | 正确。钩锁的移动特性决定了需要沿途拾取 |
| 种子生成方 | 服务端 vs Host端生成 | Host 端 Date.now() | 可行但不够稳健，未来应加入更多熵源 |
| 棋盘渲染风格 | 渐变光晕 vs 纯色实心圆 | 纯色实心圆 | 正确。清晰度高，开发期维护成本低 |
